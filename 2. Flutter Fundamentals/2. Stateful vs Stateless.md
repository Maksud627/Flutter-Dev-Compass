⇒ Basic Concept

|  | **StatelessWidget** | **StatefulWidget** |
| --- | --- | --- |
| **Meaning** | Cannot change after it's built | Can change after it's built |
| **Used when** | UI depends only on input and **never** changes | UI needs to **update dynamically** (user interaction, timers, network data) |
| **Rebuild?** | Only when external parent triggers a rebuild | Can rebuild itself by calling `setState()` |
| **Storage** | No internal mutable state | Stores mutable state in a separate **State** object |

When Flutter builds the widget tree:

- **StatelessWidget**: Flutter simply calls the `build()` method once. Done.
- **StatefulWidget**:
    - Flutter creates a `StatefulElement`.
    - Flutter also creates a separate **State** object that lives as long as the widget is alive.
    - Widget itself is immutable, but the **State object** is mutable.

🧠 *Important*: In StatefulWidget, the **Widget class is immutable**, **State class is mutable**.

- ***Stateless widget code example***
    
    ```dart
    class MyStatelessWidget extends StatelessWidget {
      final String title;
    
      const MyStatelessWidget({super.key, required this.title});
    
      @override
      Widget build(BuildContext context) {
        return Text(title);
      }
    }
    ```
    
    NB: If you want to show a static message (e.g., "Welcome!"), you don't need to ever change it use StatelessWidget.
    
- ***Stateful widget code example***
    
    ```dart
    class MyCounter extends StatefulWidget {
      const MyCounter({super.key});
    
      @override
      _MyCounterState createState() => _MyCounterState();
    }
    
    class _MyCounterState extends State<MyCounter> {
      int count = 0;
    
      void _increment() {
        setState(() {
          count++;
        });
      }
    
      @override
      Widget build(BuildContext context) {
        return Column(
          children: [
            Text('Count: $count'),
            ElevatedButton(onPressed: _increment, child: const Text('Increment'))
          ],
        );
      }
    }
    ```
    
    - When the button is pressed, `count` increases.
    - `setState()` tells Flutter: "Hey! My data changed! Rebuild this widget!"
    
- ***StatelessWidget LifeCycle***
    
    ```sql
    MyStatelessWidget
       ↓ (build)
       → Widget gets built (no extra State object)
       → Rendered on screen
       → If parent tells it to rebuild, it rebuilds fully 
    ```
    
    ✅ No memory about old stuff is kept. No `dispose()`, no `setState()`.
    
- ***StatefulWidget Lifecycle***
    
    ```sql
    MyStatefulWidget
        ↓ (createState called once)
        ↓
     _MyStatefulWidgetState
        ↓ (initState called once)
        ↓
    (build)
        ↓
    (Widget rendered with internal State)
        ↓
     User clicks something → (setState())
        ↓
    State object tells Flutter: "I changed!"
        ↓
    (build)
        ↓
    Only that widget subtree is rebuilt
        ↓
    When leaving page:
        ↓
    (dispose called)
        ↓
    State object destroyed, memory freed
    ```
    
    ✅ State object survives even when the widget rebuilds! (unless it’s removed from the tree).
    
    Here’s what happens behind the screen when you use a StatefulWidget
    
    | Phase | Method | Purpose |
    | --- | --- | --- |
    | **Creation** | `createState()` | Creates the State object |
    | **Initialization** | `initState()` | Called once when the State object is inserted into the tree |
    | **Building UI** | `build()` | Called whenever the UI needs to be rendered |
    | **State changes** | `setState()` | Marks the widget as dirty and schedules a rebuild |
    | **Updating** | `didUpdateWidget()` | Called if parent widget changes |
    | **Disposal** | `dispose()` | Called when State object is removed to clean up resources |
    
    When you open a screen with a `StatefulWidget`, this happens:
    
    ```css
    createState() -> initState() -> build()
    ```
    
    If you press a button and change state:
    
    ```css
    setState() -> build()
    ```
    
    When the widget is removed (e.g., page closed):
    
    ```css
    dispose()
    ```
    
- ***Stateful vs Stateless***
    
    
    | If UI **never changes** | use **StatelessWidget** |
    | --- | --- |
    | If UI **changes during lifetime** | use **StatefulWidget** |
    
    | Topic | StatelessWidget | StatefulWidget |
    | --- | --- | --- |
    | Memory | Lightweight | Heavier (because of State object) |
    | Performance | Slightly better if possible | Needs careful management (especially `dispose()`) |
    | UI Update | Needs parent rebuild | Self-updates via `setState()` |
    | Example Use | Static page (e.g., Terms and Conditions) | Dynamic page (e.g., Login form, Counter app) |
    
    Sequences
    
    ```sql
    StatefulWidget
        │
        ├── createState()
        │       ↓
        └── State object created
                   ↓
             initState()
                   ↓
                build()
                   ↓
        (User Interaction)
                   ↓
              setState()
                   ↓
                build() again
                   ↓
        (Remove Widget)
                   ↓
              dispose()
    ```
    
    ```sql
    StatelessWidget
          ↓
        build()
          ↓
    (rendered)
          ↓
    (recreated if parent updates)
    ```
    
- ***Common mistakes***
    - ❌ **Doing expensive work in build()**
        
        → `build()` can be called many times. Keep it fast!
        
    - ❌ **Not disposing controllers (like TextEditingController)**
        
        → Always override `dispose()` to clean resources.
        
    - ❌ **Calling setState() unnecessarily**
        
        → Only call when data that affects UI actually changes.
        
    
- ***Widget Tree & Memory Management***
    
    ```scss
     ┌───────────────────────────────────────────────┐
     │             Flutter Widget Tree                │
     └───────────────────────────────────────────────┘
    
                    ┌─────────────┐
                    │ MyApp       │ (StatelessWidget)
                    └─────────────┘
                           │
                    ┌─────────────┐
                    │ HomeScreen  │ (StatefulWidget)
                    └─────────────┘
                           │
            ┌─────────────────────────────┐
            │ Inside HomeScreen.build()    │
            │ ┌────────────┐  ┌────────────┐ │
            │ │ Text(...)  │  │ Button(...) │ (StatelessWidgets)
            │ └────────────┘  └────────────┘ │
            └─────────────────────────────┘
    ```
    
- ***Zoom into StatefulWidget memory***
    
    ```scss
    [HomeScreen] (StatefulWidget)
        │
        ├── [HomeScreenState] (State object)   <-- 🧠 Mutable
        │        ├── Variables (e.g., int counter)
        │        └── Methods (e.g., _incrementCounter(), setState())
        │
        └── (Stateless) build() UI tree (Text, Button, etc)
    ```
    
    Rebuilding flow (when something changes (e.g., tapping a button)
    
    ```scss
    User taps button ➔ Calls setState()
            ➔ Flutter marks HomeScreenState as "dirty"
            ➔ Flutter **re-calls build()**
            ➔ Updated widget subtree is re-rendered
    ```
    
- ***Summary***
    - **StatelessWidget** = No internal change.
    - **StatefulWidget** = Has internal mutable state.
    - **State object** = Lives longer, keeps data across rebuilds.
    - **setState()** = Triggers a rebuild of the widget.
    - **dispose()** = Clean up memory (important!).
    
    NB: **Flutter diffing algorithm** (Element tree comparison) is the real magic behind flutter’s performance.
